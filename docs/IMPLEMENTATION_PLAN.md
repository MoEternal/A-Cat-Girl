# 一只猫娘实施规划

更新日期：2026-07-24

## 1. 最终目标

构建一套部署在服务器上的 QQ AI 管理程序：

```text
QQ 用户
  <-> NapCat / OneBot
  <-> 一只猫娘 Python 服务
        |- 消息路由与会话队列
        |- Prompt 编译器
        |- 人设、预设与世界书
        |- 模型供应商适配器
        |- SQLite 数据库
        `- Web API / WebSocket
              <-> 浏览器管理界面
```

网页负责管理和观察，QQ 负责最终收发。第一版追求功能完整、顺序可解释、部署可靠，不投入非必要美化。

## 当前进度

配置管理版、插件管理版、统一模型运行时、同 QQ 多聊天记录和 NapCat/OneBot 私聊文本/图片闭环已完成：供应商、用户人设、角色人设、提示词模板/块、世界书是五类独立资源，组合预设引用五者并保存整套生成参数。公开插件 API、三个内置插件、OpenAI 兼容普通/流式请求、可切换会话历史、串行队列、持久动作执行器、反向 WebSocket、事件去重、安全收图、多模态单轮请求和文本/文件发送器均已交付。下一主线是测试 QQ 联调和绑定规则。详情见 `docs/CURRENT_STATUS.md`、`docs/CHAT_HISTORY.md`、`docs/PLUGIN_DEVELOPMENT.md`、`docs/RUNTIME.md` 与 `docs/ONEBOT.md`。

当前尚未接入模型聊天请求和 NapCat，因此还不是 QQ 收发闭环。

## 2. 已确定的技术方向

| 范围 | 选择 |
|---|---|
| 后端 | Python 3.11+、FastAPI、Pydantic、SQLAlchemy、Alembic |
| 依赖 | `pyproject.toml` + `uv.lock`，服务器执行 `uv sync --frozen` |
| 前端 | Vue 3、TypeScript、Vite、Vue Router；跨页面状态复杂后再引入 Pinia |
| 数据库 | SQLite + WAL；保留未来迁移 PostgreSQL 的边界 |
| QQ | NapCat + OneBot 11，优先反向 WebSocket |
| 实时更新 | WebSocket，用于日志、状态和生成进度 |
| 部署 | 当前目标为 Windows 服务器原生部署：PowerShell + `uv` + Windows 后台服务 |
| 产品名 | 界面显示“一只猫娘”，Python 包与服务名使用 `catgirl` |
| 前端交付 | 生产构建后由后端或反向代理提供静态文件，不要求服务器安装 Node.js 运行时 |

若目标服务器条件不支持上述默认项，在第 0 阶段调整，之后不随意更换技术栈。

## 3. MVP 必须具备的功能

- 多 API 供应商配置、连通性测试、启停和快速切换。
- 组合预设统一引用供应商、Prompt 模板和人设，并保存完整生成参数。
- 人设、预设、Prompt 块的增删改、复制、导入导出。
- Prompt 块拖动排序、角色选择、启停和最终消息数组预览。
- 按 QQ 好友、群聊或默认规则绑定人设、预设和模型。
- 接收 QQ 消息，构建上下文，调用模型，再把结果发送回 QQ。
- 查看会话历史、请求状态、错误日志，并支持重新生成和上下文回退。
- 群聊触发规则、白名单、并发控制、重复事件去重和失败重试。
- 数据库迁移、配置备份、恢复说明、健康检查和服务器重启自恢复。
- 管理界面登录鉴权；API 密钥不明文回显，也不写入普通日志。

## 4. 暂不进入 MVP 的内容

- 复刻其他产品的主题、动画、插件市场和网页聊天体验。
- 语音、图像生成、TTS、多人协作和应用商店。
- QQ 空间、朋友圈等非稳定接口。
- 自动 Agent、长期文件记忆、主动聊天等增强功能。这些在核心链路稳定后单独设计。

## 5. 分阶段实施

### 第 0 阶段：项目边界与验收基线（已完成）

1. 已确认 `VirtualCompanion` 是旧程序，新项目独立重建。
2. 按用户要求不读取旧程序源码，避免为复刻旧耦合浪费开发量；以后只有明确需要导入数据时才读取指定配置。
3. 已确认当前服务器为 Windows；Linux/Docker 留到正式发布阶段。
4. 已确认本机 Python 3.11、`uv`、Node.js 和 npm 工具链可用。
5. 已将首批范围锁定为供应商切换、提示词模板切换/排序和人设切换。
6. 已避开 SillyTavern 的 `8000/8001`，固定使用 `8732/8733`。

交付物：实施规划、当前状态、锁定的产品边界与第一批验收结果。

通过条件：第一批范围可独立运行和验证，不依赖旧程序代码。

### 第 1 阶段：项目骨架与可重复环境

1. 初始化 Git，加入 Python、Node、编辑器、密钥和运行数据的忽略规则。
2. 建立 `backend/`、`frontend/`、`tests/`、`deploy/` 和 `data/` 边界。
3. 配置 `pyproject.toml`、`uv.lock`、前端锁文件、代码格式化和静态检查。
4. 建立 FastAPI 入口、`/health`、统一错误响应、结构化日志和配置加载。
5. 建立 Vue 管理壳、路由、API 客户端和全局错误提示。
6. 提供 Windows 开发启动脚本；脚本负责重建环境，主程序本身不在线安装依赖。

交付物：可启动的空管理界面、健康检查、锁文件和开发说明。

通过条件：删除本地 `.venv` 和前端依赖目录后，仅按文档命令即可完整重建并启动。

### 第 2 阶段：数据库与配置模型

1. 建立供应商、模型、角色、人设版本、预设、Prompt 块、绑定规则、会话、消息、生成任务和审计日志表。
2. 所有可编辑配置增加稳定 ID、排序号、启用状态、创建/更新时间和版本字段。
3. API 密钥使用服务器主密钥加密保存；界面只返回掩码。
4. 引入 Alembic 迁移，禁止依赖启动时临时 `CREATE TABLE` 维持结构。
5. 开启 SQLite WAL、外键和合理的 busy timeout，并统一事务边界。
6. 实现 JSON 导入导出和数据库备份元数据，不把运行数据提交 Git。

交付物：首版数据库迁移、仓储层、配置 CRUD API 和测试。

通过条件：迁移可在空数据库执行，也可重复升级；敏感字段不会出现在 API 响应和日志中。

### 第 3 阶段：模型供应商适配层

1. 定义统一 `ModelProvider` 接口，隔离消息格式、参数、流式响应和错误类型。
2. 首先实现 OpenAI 兼容供应商，覆盖自定义 Base URL、模型名、请求头和超时。
3. 根据真实需求再增加 Anthropic、Gemini 等原生适配器，不在业务层写供应商分支。
4. 实现连接测试、模型配置校验、取消、超时、有限重试和错误脱敏。
5. 记录耗时、token 用量和结束原因，不记录 API 密钥和未经允许的完整敏感请求。
6. 使用假服务器完成成功、限流、超时、断流和无效响应测试。

交付物：供应商 API、统一错误模型和独立集成测试。

通过条件：切换供应商不需要修改 Prompt、QQ 或会话代码。

### 第 4 阶段：Prompt 编译器

1. 将 Prompt 建模为块，而非一整段字符串；每块包含名称、内容、角色、顺序、启用状态和插入策略。
2. 支持 `system`、`user`、`assistant` 角色及历史、记忆、当前输入等动态插槽。
3. 定义变量替换、缺失变量、空块、转义和 token 预算规则。
4. 编译器输出规范化消息数组和来源说明，QQ 处理层只能调用编译器，不能自行拼 Prompt。
5. 提供“最终顺序预览”，逐条显示角色、来源、内容摘要和预计 token。
6. 保存配置版本；编辑后可以比较和回滚，避免一次误操作破坏线上人设。
7. 为顺序、禁用块、动态插槽、角色路由、超长裁剪和供应商转换建立单元测试。

交付物：纯函数式 Prompt 编译核心、预览 API、版本快照和测试集。

通过条件：同一输入和同一版本配置得到确定结果；界面预览与实际发送内容一致。

### 第 5 阶段：人设、预设与绑定规则

1. 人设管理包括角色说明、示例对话、开场信息和可选变量。
2. 预设负责 Prompt 块组合和生成参数，人设与预设分离以便复用。
3. 支持复制、启停、导入、导出和版本回滚。
4. 建立默认、好友、群聊三级绑定，明确优先级和冲突提示。
5. 绑定结果必须可以解释：界面显示某条 QQ 消息最终命中了哪条规则。

交付物：人设/预设/绑定 API 和管理页面。

通过条件：无需修改代码即可让不同好友或群聊使用不同人设、Prompt 和模型。

### 第 6 阶段：NapCat 与消息运行时

1. 将 NapCat 封装为独立适配器，解析 OneBot 事件并统一文本、回复、提及和图片元数据。
2. 使用 `message_id` 和事件特征去重，避免重连后重复回复。
3. 每个 QQ 会话串行处理，不同会话可受控并发；设置全局并发和队列上限。
4. 实现私聊、群聊提及/关键词/前缀触发、白名单、黑名单和管理员命令权限。
5. 发送端处理超长消息分段、引用回复、超时、失败重试和可追踪错误。
6. QQ 收到消息后固定执行：规范化 -> 绑定解析 -> 写入会话 -> Prompt 编译 -> 模型调用 -> 保存回复 -> QQ 发送。
7. 图片事件必须经过媒体安全模块：CQ/mface 解析 -> 下载字节上限 -> MIME sniff -> 像素/边长限制 -> GIF 首帧/压缩 -> 只在本轮请求构造 data URI；历史只写文件名占位符，禁止写入多模态数组或 base64。
8. 使用录制的脱敏事件和假 OneBot 服务进行集成测试，再进行测试 QQ 账号联调。

交付物：完整 QQ 到模型再回 QQ 的闭环。

通过条件：断线重连、重复事件、模型超时和并发消息不会造成重复回复或会话串线。

### 第 7 阶段：会话、历史与恢复操作

1. 提供会话列表、消息详情、当前绑定和上下文预览。
2. 支持删除/禁用某条历史、回退一轮、重新生成和手动重试失败任务。
3. 每次生成保存所用人设、预设、模型和 Prompt 版本引用，保证事后可追溯。
4. 将“模型已生成但 QQ 发送失败”和“模型请求失败”区分处理，避免重复扣费。
5. 对高风险操作增加确认和审计日志。

交付物：会话管理 API、恢复操作和审计记录。

通过条件：管理员能够解释一次回复为何产生，并能在不改数据库的情况下恢复常见故障。

### 第 8 阶段：管理界面完工

页面按工作流组织：

1. 概览：NapCat、数据库、模型供应商、队列和最近错误状态。
2. 供应商：凭据、模型、参数、连接测试和默认项。
3. 人设与预设：列表、编辑、复制、导入导出和版本历史。
4. Prompt 工作台：块列表、拖动排序、角色/启用控制、编辑器和最终预览。
5. QQ 绑定：好友/群聊规则、优先级、命中模拟和冲突检查。
6. 会话：历史查看、上下文、重新生成、回退和失败重试。
7. 日志与设置：筛选、实时更新、备份和安全配置。

每页补齐加载、空数据、失败、权限不足和保存冲突状态。桌面端优先，同时保证常见手机宽度下可完成紧急管理。使用 Playwright 验证关键流程和桌面/手机布局。

交付物：完整可用的管理界面和端到端测试。

通过条件：MVP 的日常管理操作不再要求编辑源代码或直接操作数据库。

### 第 9 阶段：旧程序迁移与双轨验证

1. 编写一次性导入器，将旧配置、人设、Prompt 和必要历史转换为新结构。
2. 导入过程先生成报告，再由用户确认写入；原文件保持只读并保留备份。
3. 对相同脱敏输入比较旧程序和新程序的 Prompt 顺序、绑定结果和 QQ 输出策略。
4. 先用测试 QQ 或白名单小范围运行，再切换正式事件入口。
5. 保留明确回退步骤，在稳定观察期内不删除旧程序和旧数据。

交付物：迁移工具、差异报告、切换与回退手册。

通过条件：关键行为回归通过，用户确认正式切换，旧程序可以随时恢复接管。

### 第 10 阶段：Windows 服务器部署与运维

1. 在本地构建 Vue 前端，将静态产物纳入版本化发布包；服务器运行程序不需要 Node.js。
2. 提供 `install.ps1`：检查指定 Python 版本和 `uv`，根据 `uv.lock` 在服务器创建独立 `.venv`，并执行 `uv sync --frozen --no-dev`。
3. 将程序、环境文件、`data/`、`logs/`、`backups/` 分开；升级程序不得覆盖密钥和持久化数据。
4. 启动前执行受控数据库迁移，失败立即停止升级并保留旧版本，不允许带着半迁移状态启动。
5. 使用 WinSW 等可审计的服务包装器注册 Windows 服务，配置开机启动、异常重启、工作目录和日志轮转；计划任务仅作为不具备服务条件时的备选。
6. 提供 `update.ps1`、`backup.ps1` 和 `rollback.ps1`，升级前自动备份数据库与配置，并保留上一版程序。
7. 管理界面优先仅绑定内网/VPN 地址；若必须公网访问，则配置 HTTPS、强鉴权、访问限制和 Windows 防火墙规则。
8. 备份写入独立目录，并可复制到映射盘；定期做实际恢复演练，不能只验证备份文件存在。
9. 做完整验收：重启 Windows 服务器、重启服务、断开 NapCat、模型限流、数据库恢复和程序版本回退。
10. Linux、Dockerfile 和 Compose 不进入当前开发主线，等正式发布需要跨平台交付时再补充。

交付物：Windows 发布包、PowerShell 部署/升级/备份/回退脚本、服务配置、部署文档和发布清单。

通过条件：一台干净的目标 Windows 服务器可以仅凭发布包、服务器密钥和持久化数据恢复服务，不依赖开发机 `.venv`、Node.js 或手工安装 Python 包。

## 6. 推荐开发批次

为尽早得到可验证结果，按以下批次交付：

| 批次 | 包含阶段 | 可验证结果 |
|---|---|---|
| A | 0-1 | 环境可重建，新旧项目边界清晰 |
| B | 2-4 | 能在网页配置供应商和 Prompt，并预览准确顺序 |
| C | 5-6 | 测试 QQ 完成真实收发闭环 |
| D | 7-8 | 日常管理无需改代码 |
| E | 9-10 | 迁移完成并稳定部署到服务器 |

每个批次结束都运行现有测试、补充变更记录，并更新长期记忆。上一批次未通过验收时，不提前堆叠后一批次功能。

## 8. 开工前仍需确认

- Windows Server 的具体版本、Python 版本，以及是否允许注册 Windows 服务。
- NapCat 与新程序是否部署在同一服务器，当前使用正向还是反向 WebSocket。
- 首批必须兼容的 API 供应商及其协议差异。
- QQ 闭环后必须补齐的功能清单，尤其是图片、记忆、撤回和主动消息。
- 管理界面访问范围：仅内网/VPN，还是需要公网域名。

这些问题只影响具体实现，不影响现在确定的总体架构。

Linux 和 Docker 是正式公开发布阶段的潜在兼容目标，不作为当前服务器开发、测试或验收的依赖。
